= Implementing Event-Driven Governed Remediation with Agentic AI

In the previous modules, you explored various AI applications, including building RHEL MCP and testing access to application logs on a remote RHEL host.

In this module, you will integrate the AI and RHEL MCP capabilities built earlier with Ansible Automation Platform to complete an end-to-end process from event occurrence and analysis through remediation and validation.

This module begins with a practical scenario: `*a regular user successfully accesses an administrative page that should not be accessible*`.

This indicates that the application may have a Broken Access Control issue. After the event occurs, the system first needs to detect the anomaly and confirm the event details before determining whether further action is required; if remediation is needed, the process must also go through approval, execute the change, and finally confirm that the service has returned to normal.

The overall event-driven remediation chain is "Event Generation → Event Forwarder → EDA Rulebook → AI Analysis + RHEL MCP → Governed Workflow + Manual Approval → Validation and Recovery."

image::en@modules:ROOT:AAP_Architecture.png[Governed web remediation flow architecture,width=90%]

In this flow, Event Forwarder detects and sends events, while Event-Driven Ansible (EDA) evaluates them through the Rulebook and launches AI Analysis. AI uses RHEL MCP to gather relevant evidence from the remote host and produce analysis results and remediation recommendations. When the recommendation matches an allowed remediation action, EDA launches the AAP Governed Workflow, which first switches the website to the maintenance page and sends a notification, then deploys the repaired version after manual approval, validates the result, and finally restores normal service.

The hands-on exercises that follow will walk through this End-to-End remediation flow step by step. When complete, you will be able to observe how event detection, AI analysis, governance controls, and automated remediation are connected around the same security event.

[NOTE]
====
The Organization, Inventory, Credential, Project, Job Template, Workflow Job Template, Event Stream, and Rulebook Activation required for this lab have already been created before class. A small number of settings still need to be completed by the learner; follow the steps in this module to configure them one by one.
====

== 4. Role and Deployment of Event Forwarder

*Phase 2｜Event Monitoring and EDA Preparation*

Before deploying Event Forwarder, take a quick look at the event-driven automation flow used in this lab.

Event-Driven Ansible (EDA) is the Ansible Automation Platform component used for event-driven automation. Unlike traditional workflows in which users manually run Playbooks, EDA can continuously receive events from external systems and use a Rulebook to determine whether predefined conditions are met; when a condition matches, it triggers the corresponding AAP Job Template, Workflow, or other automation action.

The overall flow can therefore be understood as follows:

image::en@modules:ROOT:EDA_Flow.png[CVE Radar automated remediation flow,width=90%]

Event-Driven Ansible must first receive an event before it can launch the subsequent AI Analysis according to the Rulebook. In typical enterprise environments, events can be sent to the AAP Event Stream from Prometheus, Splunk, SIEM, monitoring platforms, or existing application event pipelines.

To reduce this lab's dependency on external monitoring platforms, this environment uses a customized Event Forwarder. It continuously monitors Kernel CVE Radar application logs, identifies specified security events, and forwards the event data to the learner's dedicated AAP Event Stream.

In AAP, select:

*Automation Execution → Templates*

Find:

[source,text]
----
CVE Radar - Deploy Event Forwarder
----

Open it and verify the cve_radar_event_stream_url address under Extra variables. It is recommended to copy it to a text editor for later use.

After verification, click Launch template in the upper-right corner to run it.

image::en@modules:ROOT:forwarder_run.png[Run CVE Radar - Deploy Event Forwarder,width=80%]

This Template uses Ansible to perform the following configuration on the target Edge host:

* Install the Event Forwarder program and configuration files.
* Apply the configured Event Stream URL and authentication information.
* Create and start cve-radar-eda-forwarder.service.
* Start monitoring the security event logs generated by Kernel CVE Radar.
* Route matching events to the AAP Event Stream and verify that the job completes successfully. After deployment, the Event Forwarder continues to run in the background.

== 7. Create AI Model Credential（Hands-on Configuration 1）

*Phase 3｜AI Analysis Preparation*

The CVE Radar - AI Risk Analysis Template needs to communicate with the AI Model, so you must create a Credential for the connection. Prepare the AI Model URL and Token obtained in Module 05; either of the two Models provided for this TAM Day Lab can be used.

=== Verify the Model URL and Token from the command line

Return to the terminal on the right side of this guide and enter the following content. Replace <MODEL URL>, <TOKEN>, and <MODEL_NAME> with the actual information obtained in Module 05.

[source,console,role=execute,subs=attributes+]
----
export MODEL_URL="<MODEL URL>/v1/chat/completions"
export AI_API_TOKEN="<TOKEN>"
export MODEL_NAME="<MODEL_NAME>"
----

[NOTE]
====
MODEL_URL must include /v1/chat/completions.
Set MODEL_NAME according to the selected Model: qwen3-4b-instruct or qwen3-30b-a3b-instruct-2507-fp8.
====

Run the following test:

[source,console,role=execute]
----
curl -sS \
  --connect-timeout 5 \
  --max-time 180 \
  -X POST "${MODEL_URL}" \
  -H "Authorization: Bearer ${AI_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{
    \"model\": \"${MODEL_NAME}\",
    \"messages\": [
      {
        \"role\": \"user\",
        \"content\": \"Reply with exactly: MODEL_OK\"
      }
    ],
    \"temperature\": 0,
    \"max_tokens\": 20
  }" | jq .
----

image::en@modules:ROOT:model_test.png[AI Model test command,width=80%]

The expected response should include:

[source,text]
----
"message": {
  "content": "MODEL_OK"
}
----

image::en@modules:ROOT:model_verify.png[AI Model response with MODEL_OK,width=80%]

Seeing MODEL_OK indicates that the Model is responding correctly and that the URL and Token are configured correctly.
