= 以 Agentic AI 實現事件驅動的受控修復

在前面的模組中，您已經體驗 AI 的各種應用，包括建置 RHEL MCP，並測試讀取遠端 RHEL 主機上的應用程式日誌。

在本模組中，您將把前面建立的 AI 與 RHEL MCP 能力整合至 Ansible Automation Platform。完成從事件發生、分析判斷到修復驗證的完整流程。

本模組會從一個實際情境開始： `*一般使用者成功進入原本不應該存取的管理頁面*`。

這代表應用程式可能存在 Broken Access Control 問題。事件發生後，系統需要先偵測異常、確認事件內容，再決定是否需要進一步處理；若需要修復，還必須經過核准、執行變更，最後確認服務是否恢復正常。

整體事件驅動修復鏈為「事件產生 → Event Forwarder → EDA Rulebook → AI Analysis + RHEL MCP → Governed Workflow + 人工核准 → 驗證與恢復」。

image::en@modules:ROOT:AAP_Architecture.png[受控的網頁修復流程架構,width=90%]

在這條流程中，Event Forwarder 負責偵測並送出事件，Event-Driven Ansible（EDA） 透過 Rulebook 判斷事件並啟動 AI Analysis。AI 會透過 RHEL MCP 蒐集遠端主機上的相關證據，產生分析結果與修復建議。當建議符合允許的修復動作後，EDA 會啟動 AAP Governed Workflow，先切換維護頁面並發出通知，待人工核准後部署修復版本、驗證結果，最後恢復正常服務。

接下來的實作，會一步一步完成並走過這條 End-to-End 修復流程。完成後，您可以從同一個安全事件中觀察事件偵測、AI 分析、治理控制與自動化修復如何串接在一起。

[NOTE]
====
本實驗所需的 Organization、Inventory、Credential、Project、Job Template、Workflow Job Template、Event Stream 與 Rulebook Activation，均已於課前建立。仍有少數設定需要由學員完成，請依照本模組的步驟逐項操作。
====

== 實驗目標

* 登入個人的 Ansible Automation Platform 環境。
* 確認 AAP 上預先建立的自動化資源。
* 從 AAP 部署事件轉送服務。
* 建立 AI Model Credential。
* 設定 AI Analysis 使用的 RHEL MCP Endpoint 與 AI Model Endpoint。
* 建立受控的網站修復 Workflow。
* 透過網頁操作產生 Broken Access Control 事件。
* 觀察 EDA 啟動 AI Analysis。
* 檢視 AI 蒐集的證據與修復決策。
* 核准並執行受控的網頁修復 Workflow。
* 驗證一般使用者已無法存取管理頁面。

== 4. Event Forwarder 的作用與部署

*所屬階段：階段 2｜事件監控與 EDA 準備*

在開始部署 Event Forwarder 前，先快速了解本實驗中的事件驅動自動化流程。

Event-Driven Ansible（EDA）是 Ansible Automation Platform 中用來處理「事件驅動自動化」的元件。與傳統由使用者手動執行 Playbook 不同，EDA 可以持續接收外部系統送來的事件，透過 Rulebook 判斷是否符合預先定義的條件；條件成立時，再觸發對應的 AAP Job Template、Workflow 或其他自動化動作。

因此，可以將整體流程簡單理解為：

image::en@modules:ROOT:EDA_Flow.png[CVE Radar 自動修復流程,width=90%]

Event-Driven Ansible 必須先接收到事件，才能依據 Rulebook 啟動後續的 AI Analysis。在一般企業環境中，事件通常可由 Prometheus、Splunk、SIEM、監控平台，或應用程式既有的事件管線送往 AAP Event Stream。

為了降低本實驗對外部監控平台的相依性，本環境使用客製化的 Event Forwarder。它會持續監控 Kernel CVE Radar 的應用程式日誌，辨識指定的安全事件，並將事件資料轉送至學員專屬的 AAP Event Stream。

在 AAP 中依序選擇：

*Automation Execution → Templates*

找到：

[source,text]
----
CVE Radar - Deploy Event Forwarder
----

點選進入後，確認下方 Extra variables 中的 cve_radar_event_stream_url 網址，建議先複製至記事本備用。

確認後，點選右上方 Launch template 執行。

image::en@modules:ROOT:forwarder_run.png[執行 CVE Radar - Deploy Event Forwarder,width=80%]

此 Template 會透過 Ansible 在目標 Edge 主機上完成下列設定：

* 安裝 Event Forwarder 程式與設定檔。
* 套用已配置的 Event Stream URL 與驗證資訊。
* 建立並啟動 cve-radar-eda-forwarder.service。
* 開始監控 Kernel CVE Radar 產生的安全事件日誌。
* 將符合條件的事件送往 AAP Event Stream。
等待 Job 執行完成，並確認狀態顯示為 Successful。部署完成後，Event Forwarder 會以背景服務持續執行。

== 7. 建立 AI Model Credential（實作設定 1）

*所屬階段：階段 3｜AI 分析準備*

CVE Radar - AI Risk Analysis Template 需要與 AI Model 溝通，因此必須建立連線使用的 Credential。請準備在 Module 05 取得的 AI Model URL 與 Token；本次 TAM Day Lab 提供的兩個 Model 均可使用。

=== 從命令列驗證 Model URL 與 Token

返回本說明右側的終端機操作，輸入以下內容。請將 <MODEL URL>、<TOKEN> 與 <MODEL_NAME> 替換為 Module 05 取得的實際資訊。

[source,console,role=execute,subs=attributes+]
----
export MODEL_URL="<MODEL URL>/v1/chat/completions"
export AI_API_TOKEN="<TOKEN>"
export MODEL_NAME="<MODEL_NAME>"
----

[NOTE]
====
MODEL_URL 必須包含 /v1/chat/completions。
MODEL_NAME 則根據選擇 Model，設定為 qwen3-4b-instruct 或 qwen3-30b-a3b-instruct-2507-fp8。
====

執行以下測試：

[source,console,role=execute]
----
curl -sS \
  --connect-timeout 5 \
  --max-time 180 \
  -X POST "${MODEL_URL}" \
  -H "Authorization: Bearer ${AI_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{
    \"model\": \"${MODEL_NAME}\",
    \"messages\": [
      {
        \"role\": \"user\",
        \"content\": \"Reply with exactly: MODEL_OK\"
      }
    ],
    \"temperature\": 0,
    \"max_tokens\": 20
  }" | jq .
----

image::en@modules:ROOT:model_test.png[AI Model 測試指令,width=80%]

預期回應中會出現：

[source,text]
----
"message": {
  "content": "MODEL_OK"
}
----

image::en@modules:ROOT:model_verify.png[AI Model 回應 MODEL_OK,width=80%]

看到 MODEL_OK 表示 Model 可以正常回應，且 URL 與 Token 設定正確。

=== 在 AAP 建立 Credential

從左側導覽列選擇：

*Automation Execution → Infrastructure → Credentials*

點選 Create credential，並依照以下欄位建立 Credential：

[cols="1,1",options="header"]
|===
|欄位
|建議值
|名稱
|AI Model Credentials - <MODEL_NAME>
|Credential type
|TAM Day AI Model
|AI Model URL
|<MODEL URL>/v1/chat/completions
|AI Model
|<MODEL_NAME>
|AI API Token
|貼上 Module 05 產生的 Token
|===

點選 Create credential 完成建立。您可以依需求，為本次 TAM Day Lab 提供的兩個 Model 分別建立 Credential；後續請在 AI Analysis Template 中選擇對應的 Credential 設定。

== 9. 設定告警通知（實作設定 3）

*所屬階段：階段 4｜受控修復準備*

開啟：

[source,text]

此 Template 透過 ntfy 傳送即時告警。ntfy 是輕量化的訊息通知服務，可使用簡單的 API 推送訊息，適合作為 Lab 的暫時通知媒介。在企業環境中，也可以依既有標準改用 Slack、Microsoft Teams 或其他通知工具。

在 Template 的 Extra variables 中，ntfy_url 為隨機產生的個人通知網址。將網址複製至瀏覽器，即可進入個人的訊息中心。

=== 測試發送訊息

執行此 Template，並在 Extra variables 中修改：

[source,console,role=execute,subs=attributes+]
----
ntfy_title: "這是測試訊息"
ntfy_priority: default
ntfy_tags: ""
ntfy_message: "這是測試訊息內容"
----

註：ntfy_priority 與 ntfy_tags 的可用值，可參考 ntfy publishing documentation（https://docs.ntfy.sh/publish/）。

選擇執行後，返回 ntfy_url 檢視，確認訊息已出現。

image::en@modules:ROOT:ntfy_test.png[ntfy 告警與修復完成通知,width=80%]

== 10. 建立網頁修復與告警流程（實作設定 4）

*所屬階段：階段 4｜受控修復準備*

從左側導覽列選擇：

*Automation Execution → Templates*

開啟：

[source,text]
----
CVE Radar - Governed Web Remediation
----

此 Workflow 已預先建立。當 AI Analysis 判斷下一步動作為 `repair_web_code` 時，EDA 會啟動此受控的修復流程。初始 Workflow 尚未加入執行節點，需要由您完成設定。

image::en@modules:ROOT:workflow.png[尚未設定節點的 Governed Web Remediation Workflow,width=90%]

點選右上方的 *View workflow visualizer*，再選擇 *Add step* 開始建立流程的第一個節點。

後續新增節點時，請點選來源節點下方名稱旁的三個小白點開啟選單，再選擇 *Add step and link*。此操作會新增下一個節點，並同時建立與來源節點之間的連線。

image::en@modules:ROOT:workflow_process.png[使用 Add step and link 新增下一個節點並建立連線,width=70%]

接下來請依照實際執行順序，逐步建立以下 7 個節點。

. 建立維護頁面節點
+
選擇 *Add step*，加入以下 Job Template：
+
[source,text]
----
CVE Radar - Enable Maintenance
----
+
此節點會自動連接至 Home。保留連線條件為 *Run always*。
+
Workflow 啟動後，會先將網站切換至維護頁面，避免修復期間繼續提供有弱點的管理功能。

. 建立人工核准節點
+
點選 `CVE Radar - Enable Maintenance` 節點下方名稱旁的三個小白點，選擇 *Add step and link*。
+
加入 Approval 節點，並設定：
+
[cols="1,2",options="header"]
|===
|欄位
|設定值

|Name
|Approve repaired web deployment

|Timeout
|30 分鐘
|===
+
保留 `CVE Radar - Enable Maintenance` 至 Approval 節點的連線條件為 *Run always*。
+

. 建立警告與核准通知節點

----
+

ntfy_priority: default

----
+
完成後，`CVE Radar - Enable Maintenance` 應同時連接至以下兩個節點：
+
* `Approve repaired web deployment`
* `CVE Radar - Send ntfy Alert`（警告與核准通知）

. 建立修復版本部署節點
+
點選 `Approve repaired web deployment` 節點下方名稱旁的三個小白點，選擇 *Add step and link*。
+
加入以下 Job Template：
+
[source,text]
----
CVE Radar - Deploy Repaired Website
----
+
此步驟只有在人工核准成功後才能執行，因此請調整 *Status* 欄位，將條件由預設的 *Always Run* 改為 *Run on success*。
+

. 建立修復結果驗證節點
+
點選 `CVE Radar - Deploy Repaired Website` 節點下方名稱旁的三個小白點，選擇 *Add step and link*。
+
加入以下 Job Template：
+
[source,text]
----
CVE Radar - Verify Fixed Site
----
+
將連線條件設定為 *Run on success*。
+
只有修復版本部署成功後，Workflow 才會繼續驗證網站版本與存取控制。

. 建立登入頁面恢復節點
+
點選 `CVE Radar - Verify Fixed Site` 節點下方名稱旁的三個小白點，選擇 *Add step and link*。

加入以下 Job Template：

將連線條件設定為 *Run on success*。

+
點選 `CVE Radar - Restore Login Page` 節點下方名稱旁的三個小白點，選擇 *Add step and link*。

加入以下 Job Template：

CVE Radar - Send ntfy Alert

ntfy_priority: default
ntfy_tags: "white_check_mark,robot"

== 13. 觀察 EDA 接收事件

EDA 本身不直接修復網站，而是根據已定義的規則，將事件交給 AI Analysis。

== 14. 檢視 AI Analysis

*所屬階段：階段 5｜事件分析與核准*

從左側導覽列選擇：

*Automation Execution → Jobs*

開啟最新的：

[source,text]

CVE Radar - AI Risk Analysis
----

AI Analysis 將執行以下動作：

. 接收 EDA 傳入的觸發事件。
. 取得事件中的目標主機與日誌位置。
. 連線至您的 RHEL MCP Endpoint。
. 使用核准的 MCP 工具讀取應用程式日誌。
. 將事件與日誌證據交給 AI Model。
. 產生結構化的事件判斷與修復建議。
. 將受控的 Decision Event 傳回 Event Stream。

在 Job 輸出中，於搜尋欄位選擇 `TASK` ，並在右側輸入 `Show safe investigation summary`，即可顯示該Task之輸出內容

== 您完成了什麼

恭喜您！您已完成一個受控的 Agentic AI 自動修復流程：

* 網頁操作產生真實應用程式事件。
* Event Forwarder 將事件傳送至 AAP Event Stream。
* EDA Rulebook 自動啟動 AI Analysis。
* AI 透過 RHEL MCP 蒐集遠端證據。
* AI 產生結構化且受限的修復建議。
* Decision Event 觸發 AAP Workflow。
* 人員在變更服務前進行核准。
* Workflow 執行維護、部署、恢復與驗證。
* AAP Job History 保留完整的執行與稽核紀錄。

這個架構將 AI 的分析與規劃能力，限制在企業可控、可核准且可追蹤的自動化流程中。
